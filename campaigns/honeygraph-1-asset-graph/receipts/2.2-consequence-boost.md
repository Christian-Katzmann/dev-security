# Step 2.2 — Consequence boost in the priority engine

**Phase 2 — Rank by reachable consequence.** Reachable consequence now raises
attention and re-orders cases, additively, with a plain-English reason on every
boost. Severity stays dominant; nothing is hushed.

## What changed

- **`src/security_observatory/priority.py`** — new public `with_consequence(decision, consequence)`,
  modeled on `_with_dependency_trust`:
  - **Strong path** (every hop confident, by the weakest-link rule) reaching a
    crown jewel → promotes to `fix_now` and appends e.g.
    *"This finding can reach the customer database in 2 hops, so it outranks
    higher-severity findings that reach nothing."*
  - **Weak / unknown path** → appends a "flagged for a human… low-confidence link"
    reason but **never** promotes (no escalation on a low-confidence edge).
  - **No consequence / reaches nothing** → returns the decision untouched.
  - Promote-only: it uses `_attention_rank` to ensure it can only *raise* attention,
    never lower it. Helper `_hop_phrase` renders "in 1 hop" / "in N hops".

- **`src/security_observatory/cases.py`**:
  - `_case_sort_key` / `_consequence_sort_key` — consequence is now a tiebreak
    **after** severity and **before** the title tiebreak. A crown-jewel reacher
    sorts ahead (stronger → nearer → bigger blast); everything else collapses to one
    neutral key, so no-consequence cases keep exactly today's title order.
  - `build_security_cases` now sorts via `_case_sort_key` (consequence is `None` at
    build time, so behavior is byte-identical to before).
  - New `apply_consequence_priority(cases)` — applies the boost using each case's
    attached `consequence`, then re-sorts. Returns the sorted list.

- **`src/security_observatory/scan_orchestrator.py`** — calls
  `cases = apply_consequence_priority(cases)` immediately after
  `attach_consequences(...)`. (The boost *must* run post-attach: `decide_action_level`
  at build time has no consequence data yet — consequence is computed from the asset
  graph afterward. This is why the booster is a separate additive pass rather than a
  branch inside `decide_action_level`.)

## Tests

- `tests/test_priority.py` — strong path promotes to `fix_now` with the readable
  reason; weak path explains but does not promote; unknown path does not promote;
  `None`/reaches-nothing returned unchanged; a `fix_now` finding is never demoted.
- `tests/test_cases.py` — strong consequence boosts a medium case above a
  reaches-nothing high case (which stays visible at `verify`); within one bucket the
  severity sort still wins over a weak-path low finding; no-consequence cases keep
  today's title order with empty `priority_reasons`.
- Full suite: **645 passed**.

## Acceptance

- ✅ Consequence can raise attention and re-order, but never hides a high-severity
  finding (promote-only + severity stays the dominant sort key).
- ✅ Every boost carries a non-coder-readable reason.
- ✅ Findings with no consequence data rank exactly as today (neutral sort key,
  untouched decision) — pure additive, no regression (645 tests green).
- ✅ Never auto-promotes on a low-confidence edge (weak/unknown explain only).
- ✅ Tests cover strong-boost, weak-no-boost, and no-consequence-unchanged.

## Open question — demote vs promote (surfaced, defaulted)

The MVP is **promote-only**. A high-severity finding that reaches nothing is *not*
hushed — demotion is higher-risk (it could bury a real issue if the graph is
incomplete or a crown jewel was never labeled). If we later want consequence to
quiet "reaches-nothing" noise, do it as an explicit, separately-gated step (and
likely only when `crown_jewels_defined` is true and the node is fully in the graph),
not folded into this additive booster.

## Forward sweep (for Phase 3)

- **New reason strings** 3.1 (surface) should render verbatim:
  - `"This finding can reach <jewel> in N hops, so it outranks higher-severity findings that reach nothing."`
  - `"This finding might reach <jewel> in N hops, but the path runs through a low-confidence link, so it is flagged for a human instead of being auto-promoted."`
  These live in `case.priority_reasons` alongside the dependency-trust reasons.
- **New ordering key** (`_case_sort_key`): action bucket → severity → consequence
  (reaches/strength/distance/blast) → title. 3.2 (measure) should measure the
  consequence re-ranking against this key, and can read `case.consequence` directly.
