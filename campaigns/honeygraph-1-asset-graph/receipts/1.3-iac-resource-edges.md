# Step 1.3 — Recover IaC resource edges (Checkov's discarded graph)

## What landed

Checkov's resource graph is no longer thrown away. The normalizer still keeps
`failed_checks` for findings; in parallel, a new module reads the **same raw
`checkov.json`** and recovers real per-resource identity + cross-resource
references, which become `stored_in` / `reachable_from` asset edges.

## The honest scope (the open question, answered)

Checkov's `-o json` does **not** emit its internal (networkx) resource graph — so
there is no clean graph to parse. What every check *does* carry is enough to
rebuild the load-bearing slice without a brittle full-graph parse:

- `resource` → the Terraform address (`aws_db_instance.prod`) = real per-resource identity
- `file_path` / `file_abs_path`
- `code_block` → the resource's own HCL source as `[line_no, text]` pairs

We use the address as node identity, classify data-store resource types, and
recover references by reading the HCL in `code_block` for tokens that match
another known resource address. **No Checkov command flag change was needed** —
default `-o json` already includes `resource` + `code_block` (only `--compact`
would strip them, and we don't pass it).

Because references are recovered from *source text* (not a resolved graph) and
Checkov only reports resources it ran a check on, **every IaC edge is `weak`**.
Real enough to rank on, never presented as certainty — which is exactly what
Phase 2's weakest-link rule needs (a path through an IaC edge stays weak and
must not auto-promote in 2.2).

## Edge orientation (note for 2.1)

Edges point in **blast-propagation** direction — `src` compromised ⇒ `dst`
reachable — so a forward BFS from a finding's node answers "what can this reach":

- `resource → datastore` as **`stored_in`** (resource keeps/reads data in the store)
- `secret → resource` as **`reachable_from`** (secret in that IaC file unlocks the resource)

So a secret hard-coded in `infra/main.tf` reaches the RDS database via
`secret → aws_instance.app → aws_db_instance.prod`. That secret→resource→datastore
chain is the whole reason these edges exist.

## Node derivation

`derive_asset_nodes` gained an `iac_resources` input (still the single derivation
seam used by `save_scan`). Recovered resources become **per-resource `resource`
nodes** and **`datastore` nodes** (the previously-reserved node_type, now used),
each keyed by address, confidence `weak`. When rich resources cover an IaC file,
the coarse file-level `resource` node from 1.1 is **suppressed** for that file
(no competing duplicate). When Checkov fails/times out and yields no resources,
node derivation **falls back** to the coarse file-level node from the finding —
partial scan preserved.

## Files touched

- `src/security_observatory/iac.py` — **new.** `IaCResource`, `DATASTORE_RESOURCE_TYPES`,
  `parse_checkov_resources`, `load_checkov_resources`, `derive_iac_resource_edges`.
- `src/security_observatory/asset_graph.py` — `derive_asset_nodes(iac_resources=...)`:
  mint resource/datastore nodes; suppress coarse fallback for covered files.
- `src/security_observatory/storage.py` — `save_scan(iac_resources=...)` → passes
  them to `derive_asset_nodes`.
- `src/security_observatory/scan_orchestrator.py` — `load_checkov_resources(scan_dir)`,
  pass to `save_scan`, derive IaC edges, **merge with SBOM edges into one
  `replace_asset_edges` call** (it deletes-then-inserts per scan, so the two edge
  sources must go together or the second wipes the first).
- `tests/test_iac.py` — **new**, 17 tests.

## Acceptance

- ✅ A realistic "resource references a data store" relationship becomes a
  `stored_in` edge (`aws_instance.app → aws_db_instance.prod`).
- ✅ Repos with no IaC → no resources, no edges, no crash.
- ✅ Checkov failure/timeout (no/garbage `checkov.json`) → `load_checkov_resources`
  returns `[]`, coarse fallback node still derived → partial scan intact.
- ✅ Terraform fixture test shows resource→datastore becoming an edge, plus
  secret→resource→datastore traversable in the persisted graph.
- ✅ Full suite: 615 passed.

## For the next step (2.1)

- Node identity_keys: component = `component_fingerprint`, secret = file path,
  resource/datastore = **IaC resource address** (e.g. `aws_db_instance.prod`).
  Matches what 2.1's prompt already assumes — no prompt edit required.
- `datastore` nodes are now produced (were reserved). Crown-jewel labels in 2.1
  will most naturally target `datastore` identity_keys (addresses).
- IaC edges are **`weak`**; SBOM `depends_on` edges from 1.2 are `strong`. The
  weakest-link rule will make most blast-to-crown-jewel paths weak — honest, and
  it means 3.2 may well find only the dependency-reachability signal fired
  strongly. That's expected and fine to report.
