# Step 1.2 — Recover dependency edges (the graph scanners discard)

## What landed

DëvSec runs Syft to emit CycloneDX + Syft-native SBOMs but kept only the flat
component list — the dependency *graph* in that same output was parsed and
thrown away. This step recovers it as `depends_on` asset edges between the
component nodes 1.1 already derives. No new nodes are minted.

### `src/security_observatory/sbom.py`

- **`load_sbom_dependency_edges(scan_dir)`** → `list[AssetEdge]`. Walks the same
  format-preference order as `load_sbom_components` (CycloneDX first, then Syft)
  and derives edges from the *same file* that yielded the components, so every
  edge endpoint resolves to a real node. No dependency block ⇒ `[]` (no crash).
- **`parse_sbom_dependency_edges(data, components, *, source_format)`** — pure.
  Maps each component's `bom_ref` → `component_fingerprint`, then turns declared
  relationships into `AssetEdge(edge_type="depends_on", confidence="strong")`
  addressed by `component_fingerprint`. Deduped on `(src, dst)`; self-loops
  dropped; refs with no matching component (e.g. the synthetic CycloneDX root in
  `metadata.component`) skipped rather than minted.
  - `_cyclonedx_dependency_pairs` — reads `dependencies[].ref` + `dependsOn[]`.
    Edge direction: `ref depends_on dependsOn-entry` (ref is the depender).
  - `_syft_dependency_pairs` — reads `artifactRelationships` of type
    `dependency-of`. Syft serialises this as `{parent, child}` where parent is a
    dependency *of* child, so the edge is `child depends_on parent`. All other
    relationship types (`contains`, `ownership-by-file-overlap`, `evident-by`)
    are ignored — they are not dependency edges.

### `src/security_observatory/scan_orchestrator.py`

- Loads `sbom_dependency_edges = load_sbom_dependency_edges(scan_dir)` beside the
  components, then — inside the existing `save_scan` try/finally, after
  `save_scan` has stored the nodes — persists them with
  `db.replace_asset_edges(scan_id, repo_name, edges)`. That seam (from 1.1)
  resolves each endpoint by `component_fingerprint` to a node already stored for
  the scan and **skips any endpoint that doesn't exist**, so it can never mint a
  duplicate node. No edges ⇒ no-op.

### Confidence (the honesty rule)

Both CycloneDX `dependencies` and Syft `dependency-of` are *declared* graphs, so
every edge this step emits is `strong`. This step does **no inference**, so it
emits **no `weak` edges** — the `weak` tier stays reserved for a future
heuristic linker rather than being fabricated. "Never invent certainty" cuts
both ways: we don't invent a weak link either.

## Open question — answered honestly

**Which SBOM formats DëvSec actually produces carry the dependency graph vs only
a component list?**

- DëvSec invokes Syft as `syft dir:<repo> -o cyclonedx-json=… -o syft-json=…`
  (`scanners.py:503`). Both files are written every scan; `load_sbom_components`
  (and now the edge loader) prefer CycloneDX.
- **The plumbing is universal; the signal is not.** CycloneDX's `dependencies`
  block is the reliable carrier *when populated*, but for a **directory scan**
  Syft's dependency-graph coverage is ecosystem-dependent — lockfile-based
  ecosystems (npm `package-lock.json`, yarn, etc.) get real parent→child
  relationships; many others yield a flat component list (or only a root
  component that `dependsOn` everything, whose root ref lives in
  `metadata.component` and is therefore skipped). Syft-native
  `artifactRelationships` is similarly sparse for dir scans.
- **Honest bound:** this signal is strongest on repos with a resolved lockfile
  in a graph-capable ecosystem, and degrades gracefully (flat nodes, zero edges)
  everywhere else. That bounds how universal the dependency-reachability win in
  Phase 2 can be — it is *table-stakes reachability* where the graph is dense,
  and a no-op (correctly) where the SBOM only carries a flat list. Step 3.2's
  validation must report which case the chosen repo actually fell into.

## Notes for the next steps

- **1.3** adds `reachable_from` / `stored_in` edges (resource↔datastore/secret)
  via the same `replace_asset_edges` seam. The orchestrator now already calls
  `replace_asset_edges` once for dependency edges — 1.3 must **append** its IaC
  edges to the same call (or call `replace_asset_edges` once with the combined
  list), because `replace_asset_edges` *replaces* the scan's whole edge set
  (`delete from asset_edges where scan_id = ?` first). Don't call it twice and
  clobber the dependency edges. Simplest: build one combined edge list in the
  orchestrator and persist it in a single `replace_asset_edges` call.
- **2.1** reads the graph with `list_asset_nodes` / `list_asset_edges`. Edge
  shape it can rely on: `edge_type="depends_on"`, endpoints keyed by
  `component_fingerprint`, `confidence="strong"`, **direction = depender → its
  dependency** (`src` depends on `dst`). To trace "a finding's component reaches
  a more-valuable node", follow `depends_on` edges forward (toward dependencies)
  or backward (toward dependents) per the reachability question being asked.
