## The OPEN QUESTION, answered: dependency reachability only

> *Did Campaign 1 deliver crown-jewel reachability, or only dependency reachability?*

**Only dependency reachability.** The gate note is explicit (section "The signal
that fired vs the signal that didn't"):

- ✅ **Dependency reachability fired.** A vulnerable package reaching a labeled
  high-value *component* (web server / DB client / deploy tool) via `depends_on`
  edges. Proven on Dashboard-Studio and gitslip.
- ❌ **The IaC blast-radius signal never fired — at all.** Zero `datastore` nodes,
  zero `resource` nodes, zero IaC edges, zero `weak` edges across the whole fleet
  (no Terraform exists under `~/Dev`; the datastore classifier is Terraform-only).
  The "secret → datastore crown jewel" story is **mechanism-only**, unproven on a
  real repo.

**How this reshapes Phase 1 (the honest core of this step):**

1. **The "worst node" to guard is a high-consequence *dependency/component*
   surface, not a datastore.** In practice the only crown jewels that exist are
   `component` nodes (the web server, the DB client, the deploy tool), and the only
   reachability is `depends_on`. Step 1.1's "suggest the top-consequence node" must
   rank by the real `consequence.compute_node_consequences` output (blast_radius /
   reaches_crown_jewel), and its copy must say it is guarding a **high-consequence
   dependency surface** — not imply it is guarding a database.
2. **There may be NO crown jewel at all** until a human labels one. Crown jewels
   are never inferred (`crown_jewels.py`). With no `.devsec/crown-jewels.json`, the
   graph has zero crown jewels and `reaches_crown_jewel` is always false. So Step
   1.1's suggestion must degrade honestly: rank by raw `blast_radius` when no crown
   jewel is labeled, and tell the user "label a crown jewel to make this sharper."
3. **Component crown jewels are matched by `component_fingerprint` (a 24-hex
   string), which no human can hand-author** (gate condition #2). The "plant at the
   worst node" UX is only usable if Step 1.1 lets a human pick the node from a
   human-readable list (label/package name), never by asking for a fingerprint.
4. **Weak-edge promotion is structurally untested on real data** (gate condition
   #3 — every real promotion was `strong`; zero weak edges ever existed). Step 1.1
   must not lean on weak-edge behavior as if it were proven.

None of this weakens the campaign's intent — it sharpens it. The deception loop
still runs end-to-end; it just guards the asset class Campaign 1 actually proved.

### action_level enum — the plan's "two places" is inaccurate; it is really three+ live sites and ONE silent-fallback site

This is the most important correction. The plan (Context line 17 and Step 1.2)
says the enum is "validated in two places (model.py + priority.py `ACTION_LEVELS`),
and an unknown value silently falls back to verify in both." **That is not how the
code is wired:**

| Site | Reality |
|---|---|
| **`model.py` `SecurityCase.__post_init__`** | Line **168** (plan said ~163). `self.action_level = self.action_level if self.action_level in {"fix_now","verify","watch","info"} else "verify"`. **This is the ONE and ONLY silent-fallback validation site** — and it uses an **inline literal set**, it does NOT import `ACTION_LEVELS`. Miss this one and `active_incident` is silently coerced to `verify`. |
| **`priority.py` `ACTION_LEVELS`** | Line **12**. A set — **but `grep` shows it is referenced nowhere in `src/`. It is currently dead/reference-only.** Adding `active_incident` here alone changes *no behavior*. (Still update it for consistency so it doesn't lie about the vocabulary.) |
| **`priority.py` `_attention_rank`** | Line **264** (plan said ~214). The dict `{"fix_now":0,"verify":1,"watch":2,"info":3}` that *actually* orders attention inside `with_consequence`. `active_incident` must rank **above** `fix_now` (i.e. `-1` / shift all others down). |
| **`cases.py` `_ACTION_LEVEL_RANK`** | Line **201** (plan correct). `{"fix_now":0,"verify":1,"watch":2,"info":3}` — the dict that orders cases in the list. `active_incident` must sort to the very top here too. |

**Net:** the real instruction is *"validation is one place (model.py:168); ordering
is two places (priority._attention_rank:264 + cases._ACTION_LEVEL_RANK:201); plus
the dead `ACTION_LEVELS` set for hygiene."* Step 1.2 has been rewritten to say
exactly this. (The campaign's locked-decision Context bullet is left intact as
intent — "add it to every enum site or the state vanishes" — but its parenthetical
location claim is corrected in place so an implementer is not sent to a dead set
thinking it's the validator.)
