# 2.2 — The external-confirmation boundary

> Where DëvSec's local-first guarantee ends and operator action begins, for a
> honeytoken trip to mean **"a real external attacker took the bait"** instead of
> **"something on this machine touched the decoy."**

## The gap, stated plainly

A Honey Key trip is only as meaningful as **where the decoy lives** and **where
the trigger points**. Today both are local:

1. **The decoy lives in local repo files.** `insert_honey_key_file` writes the
   decoy under the selected repo (`.devsec/honeykeys/…` by default), on the
   operator's own machine. A remote attacker never sees a file that was never
   deployed anywhere they can reach.
2. **The trigger URL points at `127.0.0.1`.** `build_decoy_snippets`
   (`honey_keys.py:134`) bakes
   `trigger_url = {base_url}/api/honey/trigger` and an `open_url` into every
   decoy, and `base_url` comes from `request_base_url()`
   (`dashboard_server.py:3722`) — the `Host` header of the **local dashboard**,
   i.e. `http://127.0.0.1:8876`. A loopback address is, by definition,
   unreachable from anywhere but this machine.

So for the loop as shipped through Step 2.1, a trip proves: *a process on this
machine (or a tool the operator ran locally) touched the decoy.* That is a real
and useful signal — it catches a curious agent, a misconfigured local job, a
script that slurped the repo — but it is **not** evidence of a remote intruder.
For a trip to mean "real external attacker," **both** local facts have to change:
the decoy must sit on a **deployed, internet-exposed surface**, and the trigger
must resolve to a **reachable collector**, not loopback.

This is the same boundary the rest of the product already draws: **External
Surface is display-only in the MVP** (`AGENTS.md`, `docs/threat-model.md`,
`README.md`). DëvSec detects and reasons locally; it does not reach out, listen
on the network, or probe targets. Whatever we build here must not quietly cross
that line.

## The honest options

### Option A — DëvSec hosts a reachable trigger collector

DëvSec would run (or operate) an internet-reachable endpoint that decoys call
home to, so a remote trip lands back in the local store.

**Rejected.** It breaks the product's spine:

- A reachable collector means a **non-loopback listener** (or a hosted service).
  Binding anything to `0.0.0.0`/LAN trips the macOS firewall dialog and the
  unattended-run contract; hosting a service makes DëvSec a network service, not
  a local-first tool, and grows exactly the External-Surface capability the MVP
  defers until approval rails exist.
- It puts DëvSec on the data path for live attacker traffic — telemetry,
  retention, and "phone-home" concerns the MCP surface explicitly disclaims
  ("No telemetry… local-only", `mcp/README.md`).
- It is not buildable headless-safely in this environment without a fake deploy,
  which the campaign forbids.

### Option B — "We mint and bind; you deploy and point it at your collector" — **CHOSEN**

DëvSec stays local-first and does the part it is uniquely good at: **mint a decoy
bound to the highest-consequence node and configure it to call back to a
collector the operator already controls.** It does **not** deploy the decoy and
does **not** host the collector. The operator:

1. Stands up a reachable collector — the simplest honest path is **exposing
   their own DëvSec dashboard's `/api/honey/trigger`** via a tunnel
   (`cloudflared`, `tailscale funnel`, an ngrok URL) or a reverse proxy in front
   of a deployed DëvSec instance. Any HTTPS endpoint that records the inbound
   request works; the existing trigger route already sanitizes and stores the hit.
2. Supplies that collector base URL to DëvSec when minting the decoy.
3. Places the decoy on the **deployed surface** they want to watch (a staging
   env file, a public bucket, a leaked-credentials canary in a deployed config)
   — operator action, outside DëvSec, by design.

DëvSec's job shrinks to: **bake the operator's reachable URL into the decoy
instead of `127.0.0.1`, validate it's a well-formed absolute URL, remember that
this key is a deployed decoy, and contact nothing.** That is the smallest piece
that makes a real external trip *possible* without DëvSec ever deploying,
listening, or phoning home.

**Why B is the honest MVP:** a local-first tool should not become an
internet-listening service to satisfy one feature. The reachable collector is a
piece of **operator infrastructure**, not a DëvSec-hosted endpoint. DëvSec
contributes the deception engineering (mint, bind, content, blast-radius
illumination on trip); the operator contributes the exposed surface and the
reachable endpoint. That division keeps every existing guarantee intact.

## What was built (the smallest honest piece)

A **deployed-decoy placement mode**. Pure minting + config; no deploy, no
listener, no network call.

- **`honey_keys.build_decoy_snippets(..., trigger_base_url=None)`** — when an
  operator-supplied `trigger_base_url` is given, the decoy's `trigger_url` and
  `open_url` are built from **that** base; otherwise they fall back to the local
  `base_url` (loopback) exactly as before. Local mode is unchanged.
- **`honey_keys.validate_collector_base_url(value)`** — accepts only an absolute
  `http(s)` URL with a host, normalizes it (strips trailing slash), and
  **never contacts it**. Junk → `ValueError` → HTTP 400. This is config
  validation, not a liveness probe.
- **`POST /api/honey/keys`** gained `placementMode` (`local` default |
  `deployed`) and `triggerBaseUrl`. In `deployed` mode a valid `triggerBaseUrl`
  is required; the minted snippets point at it and the key remembers it.
- **`honey_keys.trigger_base_url` column** (additive, idempotent — mirrors the
  `asset_node_id`/`note` columns; no `SCHEMA_USER_VERSION` bump). The store now
  records *which* keys are deployed decoys and what collector they target, so the
  dashboard/MCP can label them honestly instead of guessing.
- **Docs:** a "Deployed decoys & the external boundary" section in
  `docs/honey-keys.md` stating in plain words that DëvSec mints and binds, the
  operator deploys and hosts the collector, and a `127.0.0.1` trip is **not** a
  remote attacker.

Everything DëvSec runs still binds `127.0.0.1`. The collector URL is **text in
the decoy and a row in the local DB** — a placeholder/config value, never a host
DëvSec connects to.

## The line, in one paragraph

**DëvSec automates:** building the asset graph, choosing the
highest-consequence node, minting a powerless decoy, binding it to that node,
configuring its callback URL (loopback by default, or an operator-supplied
reachable collector in deployed mode), and — when a trip is recorded — flipping
the case at that node to `active_incident` and illuminating the blast-radius
path. **The operator must do, outside DëvSec:** stand up and expose a reachable
collector (tunnel or deployed instance), place the decoy on a real deployed
surface, and judge whether a given trip is a true external intrusion. DëvSec
never deploys a decoy, never hosts a listener, never connects to the collector,
and never claims a local trip equals a remote attacker.

## Forward sweep → Step 3.2

The boundary **confirms**, and does not weaken, what 3.2 already says: the
end-to-end demo runs against `127.0.0.1` and therefore proves **local plumbing**
— mint → bind → trip → case-flip → lit path — **not** a real external attack.
Deployed-decoy mode is **config-only** (mint + bind to an operator collector);
it does not, and cannot in a headless run, prove a remote trip. 3.2's acceptance
has been trued up with one explicit line so the verdict cannot drift into
overclaiming a remote confirmation.
