# 3.2 — Loop verdict: what the tripwire proves, and what it does not

> This is the note a reader should judge the whole Honeygraph bet on. It is
> written to be un-spinnable: every claim is bounded, and every boundary is
> stated in plain words.

## What was actually run (observed, not asserted)

The whole loop was driven **over real HTTP against a live dashboard server bound
to `127.0.0.1`** — not an in-process unit assertion. A throwaway driver booted
the production `DashboardHandler` on an ephemeral loopback port and walked the
loop across the HTTP boundary; the transcript below is its real output. The same
path is pinned as a regression test:
`tests/test_honey_keys.py::test_loop_end_to_end_over_http` (passes;
`uv run pytest tests/test_honey_keys.py` → 25 passed).

```
# Live dashboard server: http://127.0.0.1:62931  (bound 127.0.0.1, loopback only)

## Graph BEFORE the trip — GET /api/graph?repoName=repo
  scan_id=scan-1  nodes=2  edges=1  active_incident=None

## 1. Mint + bind decoy at the top-consequence node — POST /api/honey/keys (assetNodeId=1)
  key.id=0655915ecf045708  bound asset_node_id=1  placement_mode=local
  placement_notice: Local decoy: the callback points at this machine's dashboard
  (127.0.0.1). A trip means something local touched it, not a remote attacker.
  Use deployed placement to watch an exposed surface.

## 2. Trip the decoy through the live route — POST /api/honey/trigger
  response: {'accepted': True}

## 3a. Case flip — GET /api/summary
  case-web  (AT the guarded node)  action_level = 'active_incident'
    tripped node      : c80af89e25355cd515bfa4c3  (web-server@1.0.0)
    lit path          : ['e36017bd36a66dea575397a0']  (blast_radius=1)
    message           : Confirmed intrusion near this node: a decoy guarding this
      high-consequence dependency surface was triggered. This proves an adversary
      reached this region and took the bait — not that this specific finding was
      exploited. Treat every asset on the illuminated blast-radius path as
      potentially within reach.
  case-other (unrelated)           action_level = 'verify'  active_incident? False

## 3b. Lit path on the graph view — GET /api/graph
  active_incident.identity_key = c80af89e25355cd515bfa4c3  (web-server@1.0.0)
  lit path                     = ['e36017bd36a66dea575397a0']
  active_incidents lit on graph = 1  (exactly the tripped node, nothing else)

## VERDICT: loop observed end-to-end over HTTP — PASS
```

End to end, over the wire: **mint → bind → trip → flip the case at the guarded
node → light its real blast-radius path** — and *only* that node's case flips
(`case-other` stays `verify`), and *only* that node's path lights on the graph.

## What this PROVES

1. **The plumbing is real and correct.** A bound decoy, when its token hits the
   live `/api/honey/trigger` route, deterministically: opens the IR incident
   (reusing the existing `honey_incidents` lifecycle), flips the case **at the
   guarded node** to the new top state `active_incident`, and pins the node's
   real graph-traversed blast path onto the incident. Both read surfaces the
   dashboard actually uses — `/api/summary` and `/api/graph` — show the flip and
   the lit path. This is not a mocked seam; it is the production handler.

2. **IR illumination near a node.** On a trip, the operator does not get a vague
   "you might have a problem somewhere." They get: *this exact node was touched,
   and here is the set of assets reachable from it* — the blast radius to work
   outward from during incident response. The lit path is **real edge data**
   (BFS over the same adjacency the consequence score uses), not a guess.

3. **It is scoped, not greedy.** Exactly the case at the tripped node escalates.
   Cases merely *on* the blast path are illuminated but **not** escalated —
   downstream nodes are "what the intruder could reach next," not
   "confirmed-touched," and escalating them would outrun the evidence. The graph
   lights one incident, not the fleet.

4. **The honest language holds at every surface.** The message string —
   server-side constant `ACTIVE_INCIDENT_MESSAGE`, single source — says
   *"Confirmed intrusion **near** this node … not that this specific finding was
   exploited."* `/api/summary`, `/api/graph`, and the React view all render it
   verbatim. There is no copy anywhere that claims a finding was proven
   exploited.

All of the above is proven **on the dependency-reachability class** — the only
class Campaign 1 ever exercised on real data.

## What this DOES NOT prove

1. **Not a real external attacker.** The demo runs against `127.0.0.1`. The
   decoy's callback is loopback; the trip was sent from this machine. A loopback
   trip proves *something local touched the decoy* (a curious agent, a
   misconfigured local job, a script that slurped the repo) — a genuinely useful
   signal, but **not** evidence of a remote intruder. The boundary is drawn in
   full in `notes/2.2-external-confirmation-boundary.md`.

2. **Not a deployed surface.** Decoys land in local repo files. Nothing was
   deployed anywhere an outside attacker could reach. **Deployed-decoy mode is
   config-only:** DëvSec will mint + bind a decoy whose callback points at an
   operator-supplied reachable collector URL, but it **never deploys the decoy,
   never hosts the collector, and never contacts it.** A real external trip still
   requires operator action *outside* DëvSec (see "what real validation would
   require" below).

3. **Not datastore / IaC blast-radius.** The differentiated "a leaked secret
   reaches your crown-jewel database" story is **mechanism-only**. Zero datastore
   nodes, zero IaC edges, and zero weak edges ever fired on a real repo in the
   fleet (no Terraform under `~/Dev`; the datastore classifier is Terraform-only —
   Campaign 1 gate, `consequence-vs-severity.md`). The loop *can* light such a
   path mechanically, but it has never been exercised on real data. Proven only
   by unit fixtures, not by a real repo.

4. **Not "this vulnerability was the entry vector."** A trip is proximity
   evidence, not causal evidence. It says an adversary reached this region and
   took the bait — it does not say *which* finding let them in, or that any
   listed finding was used at all.

### The one distinction that must never blur

> **"Confirmed intrusion near node" ≠ "finding proven exploited."**

The first is what a trip earns. The second is what the copy is forbidden from
ever claiming. Every reason string, message, and label in the shipped loop
respects this line; this verdict exists partly to keep it respected.

## Does the loop earn its surface — vs the existing case list, and for whom?

**Yes — but only for a specific user, and only as the dependency-reachability
product.**

The existing case list answers *"what should I fix?"* — ranked, static,
pre-incident. The tripwire loop answers a different, time-critical question:
*"is someone in here right now, and what can they reach from where they took the
bait?"* That is **incident response**, not triage. The case list cannot answer
it; a flat "Honey Key triggered" alert (what DëvSec had before) answers half of
it (someone tripped something) but not the load-bearing half — *where, and
what's downstream*. The loop's blast-radius illumination is the new thing on the
surface, and it is genuinely new.

**Who it's for: the indie / solo dev shipping an internet-exposed service.** This
user has (a) a deployed surface worth attacking, (b) no SOC and no ASPM
subscription, and (c) the capacity to act on a single high-signal alert
themselves. For them, "a decoy on my exposed config was touched, and here's the
blast radius" is exactly the right shape of alert — one screen, one path,
act-now. DëvSec's edge is *local-first, single-operator IR*, not novelty: cloud
ASPM tools do dependency reachability already; what they don't do is run on one
laptop for one developer with no platform team.

**Who it is NOT for: the offline-repo hobbyist.** No exposed surface means no
external trip is ever possible; for them the loop degrades to "local plumbing
that catches local accidents" — real, but a much smaller promise. The product
must not be sold to this user as intrusion detection.

## What a real external validation would require before the claim ships

The claim *"a tripped decoy detected a real external attacker"* cannot be made
from anything in this campaign. To earn it, an operator (not DëvSec) must:

1. **Stand up a reachable collector.** Expose their own DëvSec
   `/api/honey/trigger` via a tunnel (`cloudflared`, `tailscale funnel`, ngrok)
   or a reverse-proxied deployed instance — any HTTPS endpoint that records the
   inbound hit. (DëvSec stays local-first and hosts none of this; Option A —
   DëvSec-hosted collector — was rejected in 2.2 for breaking the product's
   spine.)
2. **Mint the decoy in deployed mode** with that collector URL, so the baked-in
   callback resolves to the reachable endpoint instead of `127.0.0.1`.
3. **Place the decoy on a genuinely exposed surface** — a deployed staging
   config, a public bucket, a leaked-credentials canary — somewhere an outside
   attacker can actually find it.
4. **Observe a trip that originates off-machine** and judge it a true external
   intrusion (source IP, user agent, timing — operator judgment, outside DëvSec).

Until a trip recorded that way is shown end-to-end, the honest ceiling of the
shipped claim is: **"DëvSec mints, binds, detects-on-trip, and illuminates the
blast radius locally; turning that into proof of a remote attacker is operator
infrastructure DëvSec deliberately does not own."**

## One-line verdict

The tripwire loop is real, correct, scoped, and honestly worded — it upgrades a
flat "decoy touched" alert into "intrusion near *this* node, here's the blast
radius" for the solo dev doing their own IR — but it proves **local plumbing +
dependency-reachability illumination**, not a remote attacker, not a deployed
surface, and not the IaC/datastore story. Ship it as exactly that, and not one
sentence more.
