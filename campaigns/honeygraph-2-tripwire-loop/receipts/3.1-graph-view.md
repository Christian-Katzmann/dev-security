# Step 3.1 — The blast-radius graph view

## What this step built

The visualization deferred from Campaign 1: a dashboard **Blast radius** view that
renders the asset graph from real scan data — nodes sized by blast radius and
coloured by reachable consequence, crown jewels marked, and (when a bound decoy is
tripped) the real blast-radius path lit with a glow from the tripped node.

## Graph library choice (OPEN QUESTION answered)

**`d3-force` + hand-rolled SVG**, not react-flow or cytoscape.

- **react-flow / cytoscape** are node-editor / full graph frameworks (drag, ports,
  plugins) — tens-to-hundreds of KB for features we don't need, and their glow /
  path-highlight is fought *against* their styling, not with it.
- **d3-force** is just the layout math (~a few KB, tree-shaken). We run the
  simulation **once to a static settle** (no animation loop — kinder to the laptop,
  per the repo's heat/battery rule) and render plain SVG. SVG gives us full control
  of the glow (`<filter feGaussianBlur>`) and the lit path (just style the incident
  edges/nodes). It is the lightest thing that does glow + path-highlight cleanly.
- The whole view is **lazy-loaded** (`React.lazy`) into its own chunk
  (`BlastRadiusView-*.js`, ~29 KB / 10 KB gzip incl. d3-force) — zero weight on the
  main bundle's critical path.

## Server side

- **`consequence.build_graph_payload(node_rows, edge_rows, incidents)`** (new, pure,
  side-effect free): scores every node via `compute_node_consequences`, re-keys edges
  from storage's numeric `src_node_id`/`dst_node_id` to the `identity_key` join keys
  the front end + incident path already speak, and **scopes** the global
  `active_node_incidents()` set to only the incidents whose tripped node is in *this*
  graph (matched by rescan-stable identity). The honest `ACTIVE_INCIDENT_MESSAGE`
  rides along on each scoped incident — single source of the wording, no drift.
- **`GET /api/graph?repoPath=&repoName=`** (`dashboard_server._get_graph`): resolves
  the repo's latest scan, lists its nodes + edges + active incidents, returns the
  payload. Empty graph → empty `nodes`/`edges` + a plain `reason_none` (honest empty
  state, never a 500). Repo-scoped because the asset graph is built per scan.

## Front end

- `dashboard-ui/src/components/BlastRadiusView.tsx` — the view. Force layout computed
  once per data change; SVG render; node click → detail panel; incident → lit path +
  banner + path breadcrumb in the aside.
- Types in `dashboardData.ts`: `GraphNode`, `GraphEdge`, `GraphActiveIncident`,
  `GraphIncidentPathStep`, `GraphPayload`.
- New repo-scoped tab `blast-radius` wired into `App.tsx` (TabId, nav item w/ `Radar`
  icon, title, `viewsByMode` repo-required, route).
- CSS appended to `index.css` (`.blast-*`), reusing design tokens (`--sev-*`,
  `--brand-green`, `--ink-*`, `--r-lg`). `prefers-reduced-motion` disables the tripped
  pulse + spinner.

### Honest empty states (all three)
- **No graph data** — `reason_none` ("Run a scan to build the asset graph first" /
  "no asset-graph nodes").
- **No crown jewels labeled** — a dashed banner: nodes ranked by raw blast radius;
  label one in `.devsec/crown-jewels.json` to colour by reachability.
- **No incident** — a calm status banner; nodes still coloured by consequence, nothing
  glows.

### Honesty boundary
The incident banner + node detail show `active_incident.message` verbatim:
"Confirmed intrusion **near** this node … not that this specific finding was
exploited." No surface claims a finding was exploited.

## Performance

Nodes are capped at **240 rendered** (highest-consequence slice, crown-jewel reachers
first); above that we say so in a visible note rather than melting the frame or
silently dropping the tail. No animation loop — positions computed once, SVG static.

## Field-name forward sweep (for 3.2)

The payload matches what 2.1 emits. `active_incident` carries exactly the 2.1 shape
(`event_id, honey_key_id, triggered_at, node{node_type,identity_key,label,asset_node_id},
path[{identity_key,node_type,label,via,distance}], edges[{src_identity_key,
dst_identity_key,edge_type,confidence}], blast_radius, reaches_crown_jewel, crown_jewel,
crown_jewel_path, message}`). **New server addition for 3.2 to know:** `GET /api/graph`
(repo-scoped) and `consequence.build_graph_payload`; each graph node now also carries
the derived render fields `blast_radius`, `reaches_crown_jewel`,
`distance_to_crown_jewel`, `consequence_confidence`. Nothing 2.1 emitted was reshaped.

## Known boundaries

- The graph is per-repo (the asset graph is built per scan); the view requires a repo
  selection (repo-required tab, with its own picker empty state).
- Incident scoping joins by node identity present in the current scan's graph — the
  same rescan-stable identity 2.1 pins. An incident whose node fell out of the latest
  graph simply isn't lit (it can't be located on a graph that no longer contains it).
