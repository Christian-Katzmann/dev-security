# Step 2.1 — Trigger → flip the case → light the path

## What this step built (the bridge)

When a bound Honey Key fires, the loop now: (1) opens the incident (already done by
`record_honey_key_trigger`), (2) pins the guarded node + its real blast-radius path
onto the incident, and (3) flips the case sitting **at that node** to
`active_incident` — with honest "intrusion near this node" language, never
"exploited."

Cases are **derived per scan, not stored mutable rows**, so the flip is a *serve-time
overlay* (the same pattern as `_attach_case_decision` for suppressions), not a stored
edit. The forensic truth of the trip is pinned at trip time so it survives a later
rescan that reassigns numeric node ids.

## The rule (OPEN QUESTION answered)

> *If multiple cases sit at or near the tripped node, which flips — the nearest, or
> all on the path?*

**Only the case AT the guarded node flips.** Cases on the blast path are *illuminated*
(attached as path data) but **not escalated**. A trip proves an adversary reached
*this* node and took the bait; downstream nodes are blast radius — what they could
reach *next*, not confirmed-touched — so escalating them would outrun the evidence.
This rule lives in `apply_active_incidents`'s docstring and is asserted by
`test_apply_active_incidents_flips_only_the_node_case`.

## Payload shape for the next steps (3.1 renders, 3.2 asserts)

The flipped case carries `case["active_incident"]`:

```
{
  event_id, honey_key_id, triggered_at,
  node:    {node_type, identity_key, label, asset_node_id},
  path:    [{identity_key, node_type, label, via, distance}, ...],
  edges:   [{src_identity_key, dst_identity_key, edge_type, confidence}, ...],
  blast_radius, reaches_crown_jewel, crown_jewel, crown_jewel_path,
  message  # = ACTIVE_INCIDENT_MESSAGE
}
```

`identity_key` / `src_identity_key` / `dst_identity_key` are the join keys to the
graph payload's nodes (3.1). Which node is live = `storage.active_node_incidents()`.
**Forward sweep done:** Steps 3.1 and 3.2 prompts trued up in place to point at
`blast_radius_from`, `active_node_incidents`, and this exact shape.

## Honest boundaries / known minor gaps

- The flip is correct on the two canonical read paths (`/api/summary` +
  `scan_export`). The no-JS `dashboard_pages.py` rebuild paths are not wired for the
  honey-incident overlay (they have no incident context and are a non-primary
  surface); the React graph view in 3.1 is the intended surface.
- A user-**suppressed** case that later trips stays suppressed (suppression is an
  explicit human decision). Edge case, not special-cased.
- This proves the *loop plumbing + IR illumination near a node* on **dependency
  reachability** (the only class Campaign 1 proved on real data). It does NOT prove a
  real external attacker, a deployed surface, or datastore blast-radius — that
  honesty is Step 2.2's and 3.2's job.
