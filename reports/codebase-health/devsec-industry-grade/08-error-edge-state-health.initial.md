# Error / Edge / State Health Forensic — DëvSec (Security Observatory)

## Executive Finding

DëvSec's unhappy-path handling is, across the **scanner pipeline and backend data plane, genuinely strong** and clearly built by someone who understood that a security tool must never show a degraded scan as complete. Partial scans are labelled `partial` with explicit `evidence_gaps`; missing scanners degrade honestly (`"X is not installed or not on PATH."`); scanner timeouts are killed and reported (`exit_code 124`); malformed scanner JSON cannot crash normalization or corrupt history (`read_json_safely` + the `_dict_value`/`_dict_items` coercions); the dashboard's "What this scan covered" panel turns all of this into crafted "Checks that ran / Skipped or not installed / Cannot prove" copy. This is exactly what the Excellence Brief's `error-edge-state` cue demands, and it is well covered by tests (467 passing, including malformed-state, no-scan, empty-DB, and corrupt-rotation-file cases). The lens is **not Green overall**, though, because of three concrete gaps on the *most trust-sensitive* surfaces. (1) **Corrupt SQLite has no recovery path**: `ObservatoryDB.__init__` opens and `executescript`s the DB with no `try/except`, and I reproduced `sqlite3.DatabaseError: file is not a database` against a garbage DB file — this propagates unhandled through both the dashboard `do_GET` (no top-level handler) and the MCP `_open_db`, so a corrupted history store (a disk-full mid-write, an interrupted scan) degrades to a raw 500/traceback rather than a quarantine-and-rebuild or a calm message. (2) **The core triage write path swallows failures on the primary tab**: a failed "Mark fixed" / "Verify" decision from the Findings view routes its error into `runError`, which `FindingsView` never renders — the card simply doesn't change, a misleading silence on the exact "act" step the brief calls the product's signature. (3) **No React error boundary anywhere**, so any render-time throw (e.g. an unexpected `/api/summary` shape, since the payload is trusted with no schema guard) white-screens the whole dashboard — the "raw stack trace / dead-end UX" failure mode the brief names as first-class. None of these is a silent-egress or confident-falsehood failure; they are recovery and surfacing gaps on high-value paths.

## Top Repair Targets

1. **Make the SQLite history store self-healing (Rank 1 + 5 + 7).** Guard `ObservatoryDB.__init__` with an integrity check / `DatabaseError` catch that quarantines the corrupt file (`observatory.db.corrupt-<ts>`), rebuilds a fresh schema, and surfaces a crafted recovery state to both the dashboard and MCP. Add `tests/test_storage_corruption.py`. This closes the single highest-trust edge-state gap and is the prerequisite the GET-route wrapping (Rank 5) leans on.
2. **Stop swallowing case-decision failures on the Findings tab (Rank 2).** Give `CaseCard` a per-card pending+disabled state during the awaited mutation and surface the rejection inline on the card. Idempotent server write (`on conflict do update`) means the only real defect is invisibility — fix the surfacing and the double-submit affordance together.
3. **Add a React error boundary and a fetch-retry affordance (Rank 3 + 4).** Wrap the app in a top-level `ErrorBoundary` rendering a crafted fallback (so no payload surprise white-screens the dashboard), and add a "Retry" button to the offline/error overview state so the error path is a recovery, not a soft dead end.

## Limits

- **Read-only, no live runtime.** Per AGENTS.md and `risks.json`, I did not start the dashboard server, run `security-scan`, the installer, desktop launchers, or any process-kill. Findings about browser-visible behavior (the white-screen on a render throw, the invisible Findings-tab error, the missing retry) are grounded in code reads and the build, not a live click-through — confidence is set accordingly (Rank 3 Medium because no crash was observed live; Ranks 2 and 4 High because the code path is unambiguous).
- **Corrupt-DB reproduction was isolated.** I reproduced `DatabaseError` against a garbage file in a temp directory, never against the real `~/.security-observatory/observatory.db`, and did not exercise the unguarded path through the live HTTP/MCP servers (would require starting them) — the propagation-to-unhandled claim is inferred from the absent `try/except` in `do_GET`/`_open_db`, which is directly visible.
- **Payload-shape crash (Rank 3) is inferred.** I did not construct a malformed `/api/summary` response and feed it to the running UI; the white-screen risk follows from the trusted `response.json()` plus the absence of any error boundary, not from an observed crash.
- **Sibling-lens scope.** Visual polish/contrast of the empty/error/loading states (e.g. whether the offline note meets Mistglass/contrast standards) belongs to `design-system-accessibility-health`; the permission semantics of the MCP write path belong to `permission-boundary-health`; both are referenced, not graded here.
