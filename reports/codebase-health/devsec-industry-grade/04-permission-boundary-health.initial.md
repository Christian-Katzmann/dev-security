# Permission Boundary Health — DëvSec (Security Observatory)

## Executive Finding

The AI/MCP write boundary — the surface the Excellence Brief calls non-negotiable — is genuinely well-built and proven by an adversarial test suite: the high/critical suppression gate is a single server-side chokepoint in `storage.set_case_decision` that reads severity from the recorded case (never caller text), the MCP write tools never auto-suppress a high/critical case, the auto-merge fix path requires a clean-room approval bound to the exact diff SHA on a non-protected branch, the scan-trigger refuses arbitrary filesystem paths, and no write tool can delete findings or rewrite history. All of this passes 94 red-team and boundary tests. The material weakness is on the *other* permission surface: the local dashboard is an unauthenticated, state-mutating HTTP server on `127.0.0.1` with no Origin, Referer, Sec-Fetch, or CSRF-token check, and `read_json_body` does not even require a JSON Content-Type. The threat model honestly documents "no auth, no RBAC, localhost-only," but it stops at LAN/reverse-proxy exposure and never addresses the classic browser-borne cross-site / DNS-rebinding vector against a loopback listener — through which a malicious web page the operator visits could drive `/api/case-decision` (which the dashboard calls with `human_authorized=True`, defeating the suppression gate), honey-key file insertion, package-manager installs, scan resets, and rotation triggers. So the AI-facing boundary is excellent; the browser-facing boundary leans on an assumption ("a POST means a real human clicked") that CSRF breaks.

## Top Repair Targets

1. **Add a cross-origin / CSRF defense to the dashboard's mutating HTTP surface (Rank 1 + Rank 2).** Reject mutating `do_POST`/`do_DELETE` requests whose `Origin`/`Sec-Fetch-Site` is not same-origin (allow `null`/missing for the operator's own browser-app context as appropriate), and require `Content-Type: application/json` in `read_json_body` for mutating handlers. Deliberately exempt the honey-key trigger callback. This single fix closes the forged-suppression path that defeats the high/critical gate. Then document the loopback-browser vector in `docs/threat-model.md`.
2. **Decouple the suppression gate's "human confirmation" from "a POST arrived" (Rank 2).** Even with CSRF hardening, consider requiring an explicit per-action confirmation signal (e.g. a short-lived token rendered into the dashboard for high/critical suppressions) so the gate's authorization is positively demonstrated, not inferred from request arrival. The server-side gate in `storage.py` stays the chokepoint; this strengthens what `human_authorized=True` actually attests.
3. **Correct the MCP write-surface documentation (Undocumented Surfaces #1).** Update `mcp/README.md` so the write adapter is described as the full audited tool set (case-resolution + scan-trigger + fix-proposal/clean-room/land), with the same hard-limit framing already present in `_WRITE_MODE_BOUNDARY`. Keep the boundary truthful so the trust pitch holds.

## Limits

- **No live boundary testing.** Per the cross-lens no-live-calls guardrail and AGENTS.md, the MCP servers and the dashboard were not started, and no forged cross-origin request was actually fired. The CSRF/Origin finding (Rank 1/2) is established by code inspection (no Origin/Referer/Sec-Fetch/CSRF handling anywhere in `dashboard_server.py`, `read_json_body` accepting any Content-Type) and by the standard browser security model, not by a live exploit. Confidence is High because the absence is exhaustive in the source, but the *exploitability detail* (which browsers/preflight conditions apply to which endpoint) was not empirically confirmed.
- **macOS Keychain not exercised.** The credential-storage boundary (Rank 7) was read, not run; `security` (Keychain) calls were not invoked. Behavior on non-macOS or with a locked Keychain is unverified.
- **Scan-trigger and rotation subprocesses not run.** The `trigger_scan` / rotation-trigger paths were verified by code + tests (which stub the scanner subprocess); the real scanner/rotation binaries were not invoked (installer/scanner runs are out of bounds per risks.json).
- **Single-pass staleness.** This is an initial single-pass forensic; findings may shift slightly before repair. The MCP-boundary Greens (Ranks 3-5) are the most robust (backed by passing adversarial tests); the dashboard CSRF finding is the most likely to be addressed first and should be re-checked after any dashboard change.
