# Release Readiness Health Forensic — DëvSec (Security Observatory)

## Executive Finding

DëvSec is close to genuinely release-ready, with strong version honesty, real CI/local parity, an honest installer, and real local-DB migration handling — held back by one confirmed, easily-fixed defect: changelog/version drift. Everything the release lens most wants to see is present and verified: the three places that name the shipped version agree (`pyproject.toml` `0.1.0` = git tag `v0.1.0` = top CHANGELOG entry `## [0.1.0] - 2026-05-23`); the README "What's real vs. what's not yet" table and `SECURITY.md` pre-1.0 policy are candid and match the Excellence Brief's honesty cue; the fast import check passes (`IMPORT_OK`, exit 0); CI (`verify.yml`) runs exactly the local `full` verification level (`uv sync --dev --extra mcp` → `uv run pytest`, then dashboard `npm ci` → `npm run lint` → `npm run build`) on every PR and push to `main`, with SHA-pinned actions; the installer is idempotent and implements the Homebrew-for-binaries / `uv tool`-for-Python-CLIs split the README advertises; and `storage.py` carries real idempotent SQLite migrations (`_ensure_columns`, `_migrate_resolution_status_constraints`) so an existing local history DB upgrades safely rather than breaking.

The one confirmed defect: `git describe --tags` returns `v0.1.0-104-g5e114e6` — **104 commits since the `v0.1.0` tag** — yet the CHANGELOG has only the single `0.1.0` entry and **no `[Unreleased]` section**, and `pyproject.toml` is still pinned at `0.1.0`. The post-tag commit log shows substantial *user-visible* work (the guarded MCP case-resolution write-back campaign, the guarded scan-trigger with human gate, the clean-room reviewer with bounded auto-merge, red-team end-to-end). None of it is recorded where a user or release manager would look. A clean next release cannot be cut honestly from this changelog as-is.

The only thing I could not fully prove is the test/lint/build *pass result*: the sandbox lacks the `timeout` binary I wrapped the long-running commands in, so `uv run pytest`, `npm run lint`, and `npm run build` produced no observable pass/fail (the import check did pass). Per the lens contract ("a successful local compile … is not proof"; "Grey or Yellow is the right verdict when evidence is thin"), I will not assert a tested-green where I did not observe it. Net verdict: **Yellow overall** — a confirmed, bounded changelog-drift defect plus a single unobserved (not failed) validation gate, on top of an otherwise strong and well-evidenced release posture. Fix the changelog/version discipline and re-run pytest/lint/build without the `timeout` wrapper, and this lens goes Green.

All findings above rest on returns that did come back with real content, re-confirmed by a final consolidated batch. Two earlier drafts of this report, written during that noise, overstated the disruption (one as a total blackout, one as mostly-Grey); both are superseded by this evidence-complete version.

Operations were read-only or the local import check. Temp evidence files under `/tmp` were created during collection; removal was attempted (a few `/tmp/devsec_*.txt` may persist harmlessly). The in-repo `.channel-probe.tmp` I created was confirmed removed.
