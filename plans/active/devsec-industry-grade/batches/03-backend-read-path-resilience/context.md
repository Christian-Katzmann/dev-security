# Batch: 03-backend-read-path-resilience

## Purpose
DëvSec's pitch is "your scan history lives safely on your machine," yet the backend read path can still turn a damaged local store into a raw 500/traceback instead of a calm recovery. This batch makes the SQLite read path resilient end-to-end so a corrupt or hand-edited history file degrades to a crafted recovery state, never a crash. It owns three super-list items that all live on one fix surface — the Python read path through `storage.py` / `dashboard_server.py` / `mcp_server.py`: **S-003** (self-healing SQLite store: quarantine + rebuild on corruption), **S-006** (wrap `do_GET` routes so any read-path exception becomes a clean JSON 500), and **S-023** (guard the remaining `cases_json` JSON reads so one bad row degrades to a warning, not a payload crash).

## Non-Goals
- Do not attempt other batches' super-list items.
- Do not broaden this into a general cleanup.
- Do not make production, destructive, deploy, secret, or irreversible data changes without explicit approval.
- Do not delete or overwrite a quarantined corrupt DB — preserve it (rename to `observatory.db.corrupt-<ts>`), never `unlink` it; the corrupt bytes are the user's only path back to their history (`.adx/risks.json` `local-security-data`).
- Do not quarantine-and-rebuild on transient/environmental errors (DB locked by a concurrent writer, disk I/O): `sqlite3.OperationalError` must be re-raised untouched, not treated as corruption — destroying a healthy DB another process is mid-write on would be worse than the crash.
- Do not split or restructure `dashboard_server.py` / `storage.py` here — the god-module split is S-016/S-017 (later batches). This batch only adds read-path guards on the existing modules.
- Do not change the on-disk `cases_json` schema or normalize it into a typed table (that is the S-022/S-026 contract work); only add decode guards around the existing reads.
